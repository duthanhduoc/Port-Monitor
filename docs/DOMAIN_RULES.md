# Domain rules and invariants

These rules are the acceptance criteria for future changes.

## Identity

- A monitored port is identified by its persisted record ID; its unique natural key is the port number.
- A PID is an observation, not the identity of a monitor record.
- If the listener changes from PID A to PID B on the same port, the port record remains the same and a new observation is recorded.

## Lifecycle

```text
configured → online
configured → offline
offline → online (automatic reconnect by port)
online → offline
online → ended (process action; record remains configured)
```

`offline` means the port is still monitored but no matching listener was found during the latest sample. It does not mean “delete”.

## Sampling

- Every sample has a timestamp generated by the backend.
- Missing metrics are represented as null/unknown, not as zero.
- CPU percentage is sampled over the shared two-second refresh interval. On macOS, the app-level value is summed across its resource coalition and can exceed 100% when multiple cores are active; other platforms report the main process only.
- Memory units must be explicit at the API boundary; bytes are preferred and the UI formats them as decimal KB/MB to match Activity Monitor.
- On macOS, app-level CPU and RAM cover the app's resource coalition so they include related WebKit processes; RAM uses physical footprint to follow Activity Monitor semantics.
- History queries return chronological data and are bounded by a time range or retention limit.

## Safety and errors

- Validate ports as integers in the inclusive range 1–65535.
- Reject attempts to add a port that is already monitored.
- Never terminate a process based solely on a port that has become offline.
- The UI sends the PID that the user confirmed. Immediately before termination, verify that this expected PID is still associated with the monitored port; refuse the command if a replacement PID has taken over.
- Permission errors and unsupported metrics are visible states, not silent fallbacks.
- Removing a monitor record is separate from ending a process.

## Acceptance checklist

- Kill the process: the row remains, becomes offline, and its old samples remain queryable.
- Start another process on the same port: the row becomes online automatically and shows the new PID.
- Stop and restart repeatedly: no duplicate port records are created.
- Restart the application: configured ports and their history are loaded from SQLite.
- A failed sample does not stop monitoring other ports.
